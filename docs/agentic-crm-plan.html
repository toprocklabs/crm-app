01 · The Reframe

The CRM stops being a filing cabinet and becomes a graph that grows itself

Three shifts define everything downstream. Old CRMs are systems of record: humans type, the DB stores, reports read it back. With AI, the CRM becomes a system of action.

Rows → Graph

Accounts & contacts become nodes with typed edges: referred_by, colocated_with, introduced_by. Relationships are first-class data, not a notes field. This is the part your whole motion depends on.

Manual entry → Ambient capture

Drive docs, Gmail threads, meeting notes flow in. An agent extracts entities and proposes writes. You confirm, you don't author. The keyboard becomes the exception, not the rule.

Storage → Standing loop

Background workers wake on a schedule, read the graph, and emit next best actions — cold relationships, fresh referral paths, stuck deals — without you asking.

The one-sentence thesis: Your differentiator is trust-through-relationships. That only compounds if relationships are structured, queryable data an agent can traverse. Build the graph well and you have something Salesforce structurally cannot copy — because they don't have your trust graph.

The graph edge — one table to rule the relationships

A polymorphic edge keeps it simple: any node type → any node type. edge_type is an enum; strength decays over time without contact.

// src/lib/schema.ts — new
export const edgeType = pgEnum("edge_type", [
  "referred_by",      // the gold — your referral engine
  "colocated_with",   // same plaza/building — the Scuba Riverton play
  "introduced_by",
  "knows", "vendor_of", "customer_of",
  "partner_of", "competitor_of",
]);

export const relationships = pgTable("relationships", {
  id: serial("id").primaryKey(),
  fromType: text("from_type").notNull(),  // 'company' | 'contact'
  fromId:   integer("from_id").notNull(),
  toType:   text("to_type").notNull(),
  toId:     integer("to_id").notNull(),
  edgeType: edgeType("edge_type").notNull(),
  strength: integer("strength").default(50).notNull(), // 0–100, decays
  evidence: text("evidence"),                 // "Obsidian note 3/14" / gmail msgId
  source:   text("source").default("manual"),  // manual | drive | gmail | agent
  lastConfirmedAt: timestamp("last_confirmed_at", { withTimezone: true }),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow(),
});
Why polymorphic, not a join table per pair? You'll keep inventing edge meanings ("met at the chamber mixer", "same landlord"). One flexible edge table + an enum you extend beats five rigid join tables. Index (from_type, from_id) and (to_type, to_id) for fast traversal.

The suggestion queue schema (the autonomy gate) 
export const suggestions = pgTable("suggestions", {
  id: serial("id").primaryKey(),
  kind: text("kind").notNull(),       // 'new_contact' | 'new_edge' | 'log_activity' | 'stage_change'
  payload: jsonb("payload").notNull(), // the exact write to apply on approval
  confidence: integer("confidence").notNull(), // 0–100 from triage model
  evidence: text("evidence"),         // always cite the source
  status: text("status").default("pending"), // pending | approved | rejected | auto_applied
  autoApplied: boolean("auto_applied").default(false),
  agentRunId: integer("agent_run_id"),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow(),
});
04 · Relationship Graph — the moat

The Scuba Riverton play, made literal

"Never go in cold." Given any target, the agent traverses your private graph to find the shortest trust path — and drafts the intro ask. This is LinkedIn's 2nd-degree, except built on your real relationships instead of a public network nobody trusts.

What the agent returns

find_warm_path(target: "Riverton Yoga")
→
{
  bestPath: ["You", "Scuba Riverton", "Riverton Yoga"],
  via: "colocated_with — same plaza",
  strength: 82,
  warmth: "high",
  suggestedAsk:
    "Ask Jake (Scuba Riverton) to intro you
     to Maria next door — you fixed his
     booking flow, she has the same problem.",
  evidence: ["deal #14 won", "note 3/14"]
}

Graph primitives worth building

  • Warm-path finder — shortest trust path + drafted ask
  • Proximity clusters — geocode → plaza_key → "you own a beachhead here, here are 4 neighbors"
  • Strength decay — edges weaken without contact; surfaces "this strong relationship is going cold (94 days)"
  • Referral attribution — trace which client originated which won deal; double down on your best connectors
Relationships are assets that depreciate. Making that visible is a genuinely novel CRM primitive — it maps exactly to how trust-based selling actually works.
05 · Ambient Ingestion

Kill the keyboard — Drive & Gmail flow in on their own

A scheduled worker pulls recent files/threads, a cheap model triages whether each one even matters, then extracts entities and relationships into the suggestion queue. You approve from a clean inbox; high-confidence items auto-apply.

📁 Drive — what we extract

  • New/changed docs & sheets → company & contact mentions
  • Proposals, SOWs → deal value, stage signals
  • Intro mentions ("X connected me to Y") → introduced_by edges
  • Use: the connected Drive MCP — search_files, read_file_content

✉️ Gmail — what we extract

  • Threads with prospects → auto-log activity (type email)
  • New people on a thread not in CRM → new_contact suggestion
  • "Let me intro you to…" → referral edge with the message as evidence
  • Use: the connected Gmail MCP — search_threads, get_thread
The non-negotiable design choice: agents never write to core tables silently. They write suggestions. The suggestion payload is the exact mutation to run on approval, so "approve" is a one-click apply and "reject" costs nothing. This is what keeps your trust in the data while the system earns more autonomy over time.
06 · Autonomy & Token Economics

Autonomous — but it never blasts tokens

Your constraint: "pretty autonomous, but thoughtful, not burning through all the tokens." Four mechanisms make that true. The system spends like a careful operator, not a runaway loop.

1

Tiered models

Cheap model (Haiku) triages & scores everything. Opus is invoked only for high-value judgment — drafting an intro, deciding a stage change. Most items never touch the expensive model.

2

Scheduled, not streaming

Loops run on a cron cadence (e.g. ingestion 2×/day, brief 1×/morning), not continuous polling. Predictable, bounded spend per day.

3

Batched + deduped

Process new items in one batched pass; skip anything already seen (hash/msgId). No re-reading the same Drive folder every run.

4

Hard budget guard

Every run logs tokens to agent_runs. A daily ceiling halts loops when hit and tells you — autonomy with a circuit breaker.

07 · MCP Control Surface

You drive the whole thing by talking to Claude

Instead of building an in-app chat panel, we expose the CRM as an MCP server. You operate it from Claude desktop / Claude Code — query the graph, log activity in one sentence, review the queue. Faster to ship, and far more powerful than a textbox bolted into the web app.

MCP toolWhat it doesExample you'd say
query_graphRead nodes/edges with filters"Who referred our last 3 customers?"
find_warm_pathTrust path + drafted ask to a target"How do I get warm to Riverton Yoga?"
proximity_scanNeighbors of a customer's location"Who's in Scuba Riverton's plaza?"
log_activityNatural-language → structured write"Log that Jake intro'd me to Maria, follow up Friday."
upsert_contact / companyCreate or merge with dedupe"Add Maria Chen, owner of Riverton Yoga."
add_edgeCreate a typed relationship"Mark Riverton Yoga colocated with Scuba Riverton."

One sentence → multiple structured writes

You: "Mark Scuba Riverton as won, log that Jake
      intro'd me to the yoga studio next door,
      and remind me to follow up Friday."

Claude (via MCP):
  ✓ update_deal_stage(#14, "won")
  ✓ upsert_company("Riverton Yoga", stage:new_lead)
  ✓ add_edge(Jake → Riverton Yoga, introduced_by)
  ✓ add_edge(ScubaRiverton → RivertonYoga, colocated_with)
  ✓ create_task("Follow up Riverton Yoga", Fri)

Build approach

  • Thin MCP server (TypeScript) wrapping your existing Drizzle queries & src/app/actions.ts logic
  • Reuses Zod validation & requireUser() patterns you already have
  • Read tools open; write tools route through the same suggestion/approval rules in §06
  • Same server backs both you-in-Claude and the standing loops — one surface, no duplication
Because the loops and you both call the same MCP tools, every autonomous capability is also a manual one — and vice versa. No feature lives in only one place.
