Plan · Feature 001

Agentic referral-prospecting engine

→ Read the spec (what & why)

Approach

Evolve the pipeline we already have — Overpass sourcing → suggestions queue → /inbox + /map — into a scored, learning loop, keeping every part free/no-key and human-gated. Three things get added on top of the existing bones: a deterministic two-factor scorer (warmth × fit) that reads a stored targeting profile; an LLM "analyst" step that writes a rationale and a drafted intro for the top few prospects (tiered models, budget-guarded); and a feedback loop that turns inbox + deal outcomes into labels which periodically refine the targeting profile. The sweep is a manually-triggered server action in v1; the same function later moves behind a cron with no change to its body.

Architecture

Intake flows left-to-right into the scorer; the scorer, analyst, and ranker feed the queue and surfaces; your decisions close a loop back through Learn into the Targeting profile that the scorer reads. The profile is the thing that improves.

agent step human gate learning loop

Data flow / key decisions

  • Warmth = blended proximity + affiliation. Physical tier (same plaza > block > corridor > town) comes from coordinates we already store; affiliation comes from at least one declared-tie signal. Warmth is materialised as graph edges in the existing relationships table (colocated_with, knows, …) with a strength, so findWarmPaths() in src/lib/graph.ts picks it up for free.
  • Fit = ICP look-alike. Derived automatically from customer-stage accounts: scrape each candidate (reuse src/lib/enrich.ts), compare attributes (industry, owner-operated, storefront) to the book. No manual ICP config to start.
  • Scoring is deterministic and glass-box. A pure scoreProspect(features, profile) returns a number and a per-signal breakdown. The LLM never produces the score — it only narrates and drafts. This keeps ranking inspectable and cheap.
  • The targeting profile is the learned state. A small, versioned record holding the ICP description (LLM-written) and the feature weights (numeric, inspectable). The scorer reads the active row; the Learn step writes a new version. "Learning" = weight updates + periodic LLM rewrite of the ICP text from labelled outcomes — not a trained model.
  • Feedback already half-exists. suggestions.status gives approve/dismiss; joining an approved suggestion's created company to deals gives won/lost. Labels are computed from these — minimal new storage.
  • Tiered, budgeted agents. A cheap model triages the long candidate list; the strong model writes rationale + intro for only the top K. Every sweep records tokens/cost in agent_runs and aborts if a per-run budget is exceeded.
  • Manual now, cron later. The sweep is one server action invoked by a button; promoting it to a schedule (Vercel Cron) is a later, body-unchanged step.
  • Stay no-key. Overpass / Nominatim / Census only; adaptive radius widens the search when a customer's immediate surroundings are too sparse.

Key code

Illustrative interfaces — the shapes that anchor the design. Existing files are referenced by path rather than pasted.

The scorer (new src/lib/referral-score.ts)

type ProximityTier = "plaza" | "block" | "corridor" | "town" | "none";

type ProspectFeatures = {
  proximityTier: ProximityTier;     // physical warmth
  affiliations: string[];           // e.g. ["declared_link","same_trade"]
  icpSimilarity: number;            // 0..1 look-alike to customer book
  needSignals: string[];            // e.g. ["new_location","renovating"]
};

type TargetingProfile = {
  version: number;
  icpDescription: string;           // LLM-written, refined each cycle
  weights: Record;  // transparent, inspectable
};

type ProspectScore = {
  warmth: number; fit: number; combined: number;   // combined = warmth * fit
  breakdown: { signal: string; contribution: number }[];  // glass-box "why"
};

export function scoreProspect(f: ProspectFeatures, p: TargetingProfile): ProspectScore;

The sweep (new server action in src/app/actions.ts)

// Manually triggered from a "Scan for referrals" button on a customer / the map.
export async function scanCustomerForReferrals(formData: FormData): Promise<void> {
  // 1. source nearby (Overpass, adaptive radius)  -- promote scripts/source-nearby.mjs
  // 2. qualify (enrich.ts) + extract ProspectFeatures
  // 3. score (referral-score.ts) against active TargetingProfile
  // 4. analyst pass on top K (Haiku triage -> Opus draft), budget-guarded via agent_runs
  // 5. upsert scored rows into `suggestions` (payload extended below), revalidate /map + /inbox
}

Extended suggestions.payload (jsonb — no migration needed)

{ name, category, address, lat, lng, nearCompanyId, nearCompanyName, distanceMeters,
  warmth, fit, combined,            // scores
  proximityTier, affiliations,      // warmth evidence
  icpSimilarity, needSignals,       // fit evidence
  rationale, draftedIntro }         // analyst output (top K only)

Implementation steps

  1. P1Deterministic scoring. Add referral-score.ts; extend the suggestion payload with warmth/fit/breakdown; compute during sourcing; sort the inbox + map by combined and show the scores. Add adaptive radius. (No LLM, no schema change.)
  2. P2In-app manual sweep. Promote scripts/source-nearby.mjs into scanCustomerForReferrals; add a "Scan for referrals" button per customer and on /map. Scaffold agent_runs logging + budget guard (even before any model call).
  3. P3Analyst pass. Add the tiered LLM step (cheap triage → strong draft) that writes rationale + draftedIntro for the top K; surface "Draft intro for <contact>" in the popup/inbox card.
  4. P4Beyond proximity. Implement the first non-geographic warmth signal (declared digital ties via the scraper, and/or complementary-trade affinity seeded by the LLM). Each becomes a weighted feature.
  5. P5Learning loop. Add the targeting_profile store; a "Refine targeting" run that reads approve/dismiss/won/lost, rewrites the ICP text, and nudges weights; scorer reads the active profile; expose a read-only "why these weights" view.
  6. P6Cadence (later, out of v1). Move the unchanged sweep behind a Vercel Cron once it has earned trust; keep the manual trigger as an override.

Risks & tradeoffs

Risk / tradeoffMitigation
OSM/Overpass coverage is sparse outside dense strips (e.g. Coatary's area returned zero).Adaptive radius; keep the Google Places swap one env-key away; never present "no pins" as "no prospects."
LLM cost / runaway loops.Tiered models, top-K only, agent_runs budget guard that aborts the sweep, and manual triggering caps volume in v1.
Over-fitting to scant early feedback.Seed the profile from the current customer book; require a minimum sample before weights move; keep a human in the loop on every action.
Wrongly asserting two owners know each other.Always frame as "likely," show the evidence, let the user dismiss — and feed that dismissal back as a negative label.
Awkward or off-brand intro drafts.The agent drafts; the human edits and sends. No auto-send in v1.
Scraping reliability / politeness (Overpass, sites).Best-effort no-throw (as in enrich.ts/geocode.ts), polite rate limits, cache via place_enrichment.

Verification

  • A manual scan of Scuba Dive Utah returns scored, ranked prospects with a visible per-signal breakdown; npm run lint + npm run build stay green.
  • Repeatedly dismissing a category (e.g. restaurants) demonstrably lowers its rank in the next sweep — captured as a before/after.
  • A sweep forced past its token ceiling aborts cleanly and records an agent_runs row with the spend.
  • Existing /inbox approve/dismiss and /map interactions are unchanged (no regression).
  • Every drafted intro is shown for human approval before any send path exists.
