Plan · Feature 002

Proposal creator merge — implementation plan

Four phases: data model → CRM-hosted proposal pages & signing → backfill of existing agreements → creation flow and decommission. Each phase ships independently.

Architecture decisions

  • Content model: keep markdown. The proposal body stays the existing four-section markdown (Overview / Pricing table / What's Included / Notes) stored in proposals.contentMd. It's already the authoring format, diffs well, and the renderer parses it the same way build_proposal.py does. No structured pricing schema in v1.
  • PDF storage: Postgres bytea on Neon. Volume is ~10 documents at a few hundred KB each; a blob store is not warranted. Column on the proposal row; served via an authenticated route handler. Revisit only if size becomes real.
  • Signed PDF produced client-side, exactly as today (the page already builds the PDF in-browser and POSTs base64). The server action validates size/type, stores it, and fires side-effects — this is a near drop-in replacement for the Apps Script endpoint.
  • Public route carve-out. /p/* skips the auth redirect (like /login); protection is the per-proposal PIN. PIN check happens server-side (POST → sets a short-lived signed cookie scoped to that slug) instead of today's client-side JS check — mild security upgrade, same UX.
  • Email: decide at P2 kickoff. Default recommendation is Resend (one env key, ~10 lines); fallback is keeping the existing Apps Script webhook purely for notification (it already works, zero new keys) while the PDF stays in the CRM either way.

Data model

// src/lib/schema.ts additions
proposalStatusEnum = pgEnum("proposal_status",
  ["draft", "sent", "viewed", "signed", "declined", "superseded"]);

proposals = pgTable("proposals", {
  id: serial,
  companyId:  integer → companies.id   (not null)
  dealId:     integer → deals.id       (nullable)
  contactId:  integer → contacts.id    (nullable; signer/POC)
  title:      text                     // "Pacific Scuba — Website & Intake"
  slug:       text unique              // hosted URL: /p/[slug]
  pin:        text                     // client PIN; internal master PIN via env
  status:     proposal_status default 'draft'
  contentMd:  text                     // four-section markdown body
  clientName: text, business: text     // header fields (from old frontmatter)
  signedPdf:  bytea (nullable)         // custom Drizzle bytea type
  signerName: text, signedAt: timestamp
  sentAt / firstViewedAt: timestamp    // R10
  createdAt / updatedAt
});

Follow the repo's DB workflow: schema edit → db:generate → review SQL → db:push (push is source of truth per known drizzle-meta drift).

Phases

Phase 1 · Foundation

Schema + internal CRM surfaces

  • Add proposals table + enum; migrate.
  • /proposals list page (status pills, linked account/deal) in the existing Gong-style shell; add to nav in crm-shell.tsx.
  • Proposal panels on /accounts/[id] and /opportunities/[id].
  • Server actions: createProposal, updateProposal (Zod-validated, requireUser()-gated), plus authenticated GET /proposals/[id]/pdf download.

Done when: a proposal row can be created/edited in-app and shows on its account. ~1 session.

Phase 2 · Client-facing

Hosted proposal page + signing

  • Port proposal.html.j2 to /p/[slug]: PIN gate (server-checked, signed cookie), branded render of contentMd, terms page, signature pad (keep signature_pad + client-side PDF build).
  • signProposal server action: validate → store PDF bytea + signer/date → status signed → log activities row on the account → notify (Resend or legacy webhook) → if dealId set, surface "mark deal won?" on the opportunity page (R9, human-confirmed).
  • Record firstViewedAt on successful PIN entry (R10 cheaply).
  • Verify the CRM's public deployment serves /p/* unauthenticated; middleware/auth carve-out tested.

Done when: a test proposal is signed end-to-end on the deployed CRM and the PDF lands on the record. Pixel-compare against a current hosted proposal for brand parity. ~1–2 sessions.

Phase 3 · Backfill

Import the 8 existing proposals + signed agreements

  • One-off script scripts/import-proposals.mjs: parse each proposals/<slug>/proposal.md (frontmatter + body) → match business name to companies (create if missing, correct stage) → insert proposal rows preserving slug + PIN so existing client URLs can be redirected or re-issued.
  • Collect signed PDFs from the Drive folder (manual download to a local dir the script reads — simplest, no Drive API) and attach; mark those signed with best-known dates. Unsigned ones become sent.
  • Log a backdated signed proposal activity per signed agreement.
  • Human review pass in the CRM: every proposal on the right account, right status.

Done when: spec success criterion #1 holds — every historical signed agreement is on its account and downloadable. ~1 session, plus a manual Drive download.

Phase 4 · Consolidate

Prompt-driven creation + decommission

  • Document the creation prompt-flow in AGENTS.md: paste/point at a transcript → Claude Code drafts the four-section markdown honoring toprock_branding.md rules (copied into this repo) → calls createProposal via a script or the app → Austin reviews in-app → sends link.
  • Point any live client URLs at the CRM (Vercel redirect from the old proposal site, or re-send new links).
  • Archive proposal_creator (README pointer: "merged into crm-app, plan 002"); stop deploying it.

Done when: a new proposal ships start-to-finish from this repo only. ~1 session.

Risks & mitigations

Auth carve-out for /p/* accidentally exposes CRM pagesCarve-out is an explicit path allowlist; verify guarded routes still redirect (existing validation checklist).
CRM not publicly deployed / clients can't reach pagesResolve spec open question before P2; deployment is a P2 prerequisite, not an afterthought.
Backfill mismatches (business names ≠ account names)Script proposes matches, human confirms; only 8 records — review each.
Losing the still-working legacy flow mid-migrationproposal_creator stays untouched and deployable until Phase 4 parity check passes.

Out of scope (per spec)

Proposal redesign, DocuSign-style providers, general file storage, multi-tenant permissions. DOCX export only if it turns out to still be needed after the hosted flow is canonical.
