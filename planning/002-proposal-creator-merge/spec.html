Spec · Feature 002

Merge the proposal creator into the CRM

Fold the standalone proposal_creator tool into Toprock CRM so proposals and signed agreements become first-class records tied to accounts and opportunities — one tool, one place.

Problem

Proposals live in a separate repo (proposal_creator) with its own workflow: a markdown file per client → a Python script builds a branded DOCX and a PIN-gated hosted HTML page (static, deployed on Vercel) → the client signs in-page → a Google Apps Script webhook saves the signed PDF to Google Drive and emails both parties.

The CRM — the system of record for accounts and deals — never learns any of this happened. Signed contracts sit in a Drive folder; proposal state (drafted / sent / viewed / signed) exists nowhere; and creating a proposal means switching repos and tools.

Concretely: 8 client proposal folders and 7+ generated DOCX files exist today with no link to the companies or deals rows they belong to.

Target workflow

1 · Create

Prompt the CRM (Claude Code session in this repo, or an in-app form) with a transcript or pricing notes. A proposal record is created against the account/opportunity.

2 · Send & sign

The CRM serves the PIN-gated proposal page itself. The client signs in-page; the signed PDF and timestamp land on the proposal record.

3 · Track

Proposal status is visible on the account and opportunity detail pages; signing logs an activity and can advance the deal stage.

Goals

  • Proposals as CRM entities. A proposals table linked to companies (required) and deals (optional), with a status lifecycle and the signed PDF attached.
  • One creation surface. Author proposals by prompting this repo's Claude Code (the established pattern here — same as enrichment) with markdown content stored in the DB, not loose files in another repo.
  • CRM-hosted signing. Replace the static Vercel site + Apps Script webhook with CRM routes and server actions, preserving the exact client-facing experience (branding, PIN gate, signature pad, confirmation email).
  • Backfill. Import all 8 existing client proposals and every signed agreement, matched to their accounts.
  • Decommission. Retire proposal_creator once parity is verified, so there is exactly one tool.

Non-goals

  • No redesign of the proposal look. The client-facing page and brand rules (fonts, palette, tone in toprock_branding.md) carry over as-is.
  • No general document management. This stores proposals and their signed PDFs — not an arbitrary file cabinet per account.
  • No e-signature service integration (DocuSign etc.). The existing lightweight signature-pad flow has worked with real clients; keep it.
  • No multi-tenant / per-user permissions. Same single-tenant model as the rest of the CRM.
  • DOCX generation is optional to carry over. The hosted page + signed PDF is the primary artifact; keep the Python DOCX script only if it's still actually used (open question).

Success criteria

  • Every historical signed agreement is attached to the correct account in the CRM and downloadable from it.
  • A brand-new proposal can go transcript → live PIN-gated page → client signature → signed PDF on the account without touching the proposal_creator repo.
  • A signed proposal is visible on the account and opportunity pages, with an activity logged at signing time.
  • The client-facing page is visually indistinguishable from the current hosted proposals (brand parity).
  • proposal_creator can be archived with nothing lost.

Open questions

  • Where do signed PDFs live? Postgres bytea in Neon (zero new infra; volume is tiny — recommended), vs. Vercel Blob / S3. Affects R8.
  • Is the CRM publicly deployed? The proposal page must be reachable by clients. If the CRM is local-only today, deployment (Vercel) becomes a prerequisite for R2.
  • Email sending mechanism for R4 — a transactional provider (e.g. Resend) needs a key; alternatively keep the existing Apps Script webhook as a stopgap and swap later.
  • Is the DOCX still needed once the hosted page + signed PDF is canonical, or was it a stepping stone? Determines whether R11 exists at all.
  • Terms of service page (terms.html.j2) — one shared CRM route, or per-proposal snapshot of the terms as signed?
