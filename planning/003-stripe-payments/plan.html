Plan · Feature 003

Stripe payment mirror — implementation plan

Three phases: mirror the data and link it to accounts → surface it on the account page → keep it live with a webhook. Each ships independently and delivers value on its own.

Architecture decisions

  • Stripe is the source of truth; the CRM is a cache. Every row we store is reconstructable by re-running the backfill. That makes the mirror safe to wipe and rebuild, and means a sync bug can never corrupt billing reality — only our view of it.
  • Mirror at the charge level, not the invoice level. Billing is inconsistent today (subscriptions, one-off invoices, and ad-hoc links all in play). Every successful payment produces exactly one charge regardless of origin, so charges are the one ledger that can't miss money. Invoice and subscription IDs ride along on each charge row for context.
  • Normalize subscription amounts to monthly at write time. A yearly plan is stored as monthlyAmountCents = annual / 12. Doing this on the way in means every read is a plain SUM() and can be compared directly against deals.valueCents, which is already MRR.
  • Restricted, read-only API key. The spec says read-only; the key enforces it. Grant read on Charges, Customers, Subscriptions, Invoices — nothing else. A code bug then cannot charge a client, which is a far stronger guarantee than our own discipline.
  • Payments are stored even when unattributable. payments.companyId is nullable and stripeCustomerId is always recorded. Money is never dropped because we couldn't guess the account; it just shows up as unlinked until a human assigns it.
  • Linking is retroactive. Linking an account to a Stripe customer re-attributes all previously-synced payments for that customer. Without this, anything synced before the link would stay orphaned forever.

Data model

// src/lib/schema.ts additions

companies.stripeCustomerId: text          // nullable, unique index

paymentStatus = pgEnum("payment_status",
  ["succeeded", "refunded", "partially_refunded", "failed"]);

payments = pgTable("payments", {
  id: serial
  stripeChargeId:       text NOT NULL     // ch_... — unique, the idempotency key
  companyId:            integer -> companies.id (nullable, ON DELETE set null)
  stripeCustomerId:     text              // always recorded, even when unlinked
  amountCents:          integer NOT NULL  // gross the client paid
  refundedCents:        integer default 0
  currency:             text default 'usd'
  status:               payment_status
  description:          text
  receiptUrl:           text              // deep link back into Stripe
  stripeInvoiceId:      text              // nullable
  stripeSubscriptionId: text              // nullable — ties a payment to recurring
  livemode:             boolean NOT NULL  // test-mode rows can never inflate totals
  paidAt:               timestamp
  syncedAt:             timestamp
}, indexes: unique(stripeChargeId), (companyId), (paidAt), (stripeCustomerId))

stripeSubscriptions = pgTable("stripe_subscriptions", {
  id: serial
  stripeSubscriptionId: text NOT NULL     // sub_... — unique
  companyId:            integer -> companies.id (nullable)
  stripeCustomerId:     text
  status:               text              // active | past_due | canceled | trialing | unpaid
  monthlyAmountCents:   integer NOT NULL  // normalized; see below
  interval:             text              // month | year — kept for display
  currentPeriodEnd:     timestamp
  canceledAt:           timestamp
  livemode:             boolean NOT NULL
  syncedAt:             timestamp
}, indexes: unique(stripeSubscriptionId), (companyId), (status))

Follow the repo's DB workflow: schema edit → db:generate → review SQL → db:push (push is source of truth per the known drizzle-meta drift).

MRR normalization

A Stripe subscription can bill on any interval. Normalize each subscription item to a monthly figure so one SUM() answers "what is this account billed per month":

// per item: unit_amount * quantity, then by price.recurring
month,  interval_count = 1  -> amount
month,  interval_count = 3  -> amount / 3      // quarterly
year,   interval_count = 1  -> amount / 12
week,   interval_count = 1  -> amount * 52 / 12
// round to whole cents; sum items -> monthlyAmountCents

Real vs. expected MRR

The comparison that makes this worth building. Both sides are one query:

expected = SUM(deals.value_cents)              WHERE company_id = ? AND stage = 'won'
actual   = SUM(subs.monthly_amount_cents)      WHERE company_id = ? AND status IN ('active','trialing')
ConditionMeaningShown as
actual == expectedBilling matches what was sold.Matched (green)
actual < expectedUnder-billing — subscription never created, cancelled, or set too low.Shortfall + amount (red)
actual > expectedBilling more than the CRM records — likely a stale/missing won opportunity.Over (amber)
expected > 0, actual == 0Sold but never billed. The expensive one.Not billing (red)
This is a display-only comparison in v1 — it reports the discrepancy, it does not act on it. No alerts, no auto-fix, nothing written to Stripe.

Sync flows

Backfill (history)

scripts/import-stripe.mjs, following the shape of scripts/import-proposals.mjs: idempotent, --dry-run capable, safe to re-run.

node scripts/import-stripe.mjs [--dry-run] [--since 2026-01-01] [--live-only]

  1. page through stripe.charges.list({ limit: 100 }, expand payment intent)
  2. page through stripe.subscriptions.list({ status: 'all', limit: 100 })
  3. resolve companyId for each stripeCustomerId (see linking below)
  4. upsert by stripeChargeId / stripeSubscriptionId — ON CONFLICT DO UPDATE
     so re-running corrects drift instead of duplicating rows

Webhook (live)

src/app/api/stripe/webhook/route.ts — public by necessity, protected by signature, never by session.

export const runtime = "nodejs";      // Stripe SDK needs node crypto
export const dynamic = "force-dynamic";

const body = await request.text();    // RAW body — required for signature check
const event = stripe.webhooks.constructEvent(
  body, request.headers.get("stripe-signature"), process.env.STRIPE_WEBHOOK_SECRET
);                                     // throws -> 400, nothing written

charge.succeeded / charge.updated          -> upsert payment
charge.refunded                            -> update refundedCents + status
customer.subscription.created|updated|deleted -> upsert subscription

Route handlers don't call requireUser(), so no auth carve-out is needed — but the handler must refuse to run at all if STRIPE_WEBHOOK_SECRET is unset, rather than silently accepting unsigned posts.

Assignment uses the same autosave-select pattern as updateProposalDeal from plan 002. On link, run the retroactive attribution:

UPDATE payments             SET company_id = ? WHERE stripe_customer_id = ?;
UPDATE stripe_subscriptions SET company_id = ? WHERE stripe_customer_id = ?;
UPDATE companies            SET stripe_customer_id = ? WHERE id = ?;

Phases

Phase 1 · Data

Schema, backfill, and linking

  • Add stripe dependency; add STRIPE_SECRET_KEY (restricted read-only) and STRIPE_WEBHOOK_SECRET to .env.local.
  • Schema: payments, stripe_subscriptions, companies.stripeCustomerId; generate + push.
  • src/lib/stripe/client.ts (SDK singleton) and src/lib/stripe/normalize.ts (monthly normalization, charge → row mapping) — pure functions, so the tricky math is testable without hitting the API.
  • scripts/import-stripe.mjs with auto-link + a printed report of what linked, what was proposed, and what stayed unlinked.

Done when: a dry run prints a sane match report, and a real run makes SELECT SUM(amount_cents) FROM payments reconcile against the Stripe dashboard total. ~1 session.

Phase 2 · Visibility

Billing panel and payments page

  • src/components/billing-panel.tsx — server component in the shape of proposals-panel.tsx: lifetime paid, active subscription + status pill, real vs. expected MRR, recent payments with Stripe receipt links.
  • Mount on /accounts/[id]; add the MRR comparison to /opportunities/[id] (R12).
  • /payments list page + nav entry, including the unlinked-customers section and the account-assignment control.
  • Money formatting reuses currency from @/lib/format; status pills follow the proposal-status-ui pattern.

Done when: the stated outcome is met — open an account, see what they've paid — and any real MRR discrepancies are visible. ~1 session.

Phase 3 · Automation

Webhook for live sync

  • Webhook route with signature verification; register the endpoint in Stripe against the Vercel deployment.
  • Test locally with stripe listen --forward-to localhost:3000/api/stripe/webhook and stripe trigger charge.succeeded.
  • Verify idempotency by replaying the same event twice — the row count must not change.
  • Document the setup + env vars in AGENTS.md.

Done when: a real payment appears on the account within seconds, with no script run. ~1 session.

Risks & mitigations

RiskMitigation
Forged webhook posts fake payments into the ledgerMandatory Stripe signature verification; handler hard-fails when the secret is missing rather than accepting unsigned requests.
Test-mode data inflates real revenue numberslivemode column on both tables; every total filters on it.
Double-counting from webhook retries or repeated backfillsUnique index on the Stripe ID + ON CONFLICT DO UPDATE; verified by replaying an event.
Payments synced before an account is linked stay orphanedLinking triggers retroactive re-attribution by stripeCustomerId.
A code bug charges a real clientRestricted read-only API key — the capability doesn't exist. Verify by attempting a charge and expecting a permissions error.
Money collected outside Stripe makes "lifetime paid" wrongOpen question in the spec; if confirmed, R15 (manual payment entry) is promoted to Must before Phase 2 ships.
Non-USD charges silently mis-summedcurrency stored per row; totals filter to a single currency and flag anything else rather than adding across currencies.

Out of scope (per spec)

No writes to Stripe, no dunning or collections workflow, no customer-facing billing portal, no accounting/revenue-recognition export. Overdue-invoice surfacing and generating invoices from a signed proposal are the natural follow-ons once the mirror is trusted — both would be a new plan, not an edit to this one.
