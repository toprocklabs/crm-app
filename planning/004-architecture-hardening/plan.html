Plan · Feature 004

Architecture hardening — an architect's review

Fourteen findings from five review passes over the existing codebase, sequenced strictly by blast radius. Nothing in Tier 0 or Tier 1 can change observable behaviour; the riskier work is quarantined at the end where it can be deferred indefinitely without stranding anything before it.

Deviation 1 — F08 was wrong about the cause. The plan asserted the ten auto-save components were one pattern that had drifted, and proposed converging them on the optimistic click-to-edit behaviour. Reading all ten showed three deliberate interaction families: click-to-edit (company field, proposal PIN), always-visible input saving on blur (contact, deal, activity date), and select saving on change (the five dropdowns). Converging them would have redesigned four pages — a violation of this plan's own safety contract. What shipped instead extracts the shared machinery into auto-save-hooks.ts and leaves every component's markup untouched, so the refactor is genuinely invisible.

Deviation 2 — F05's wrapper is not generic over FormData. A generic marshaller would turn id: raw ? Number(raw) : undefined into z.coerce.number() applied to "", which coerces to 0 and fails .positive() — a silent regression on every blank optional dropdown. Each action keeps its explicit input mapper; the wrapper's job is making requireUser() structural, which it does: requireUser no longer appears in actions.ts at all.

Correction to F11. The finding claimed /accounts/99999 was "a crash, not a 404". All four [id] routes already called notFound() — the real gap was that no not-found.tsx existed to style it, so it rendered Next's default. The error-boundary half of the finding stood as written and was the higher-value fix.

F04 was cheaper than budgeted. The risk table planned a checksummed copy of every signed PDF. The database holds seven proposals and zero stored PDFs (the plan-002 backfill still needs a manual Drive download), so there was nothing to migrate — only the read and write paths changed.

One real bug caught during verification. The hasSignedPdfExpr predicate first interpolated Drizzle column objects into a sql template. Drizzle emits those unqualified, so ${'{'}proposalDocuments.proposalId{'}'} = ${'{'}proposals.id{'}'} rendered as "proposal_id" = "id" — and inside SELECT 1 FROM "proposal_documents" both resolve to that table. The correlation silently evaporated and the predicate was always false, which would have meant the download link never appearing for a newly signed proposal. Typecheck and build were both clean; only executing it against the database exposed it. Identifiers are now written out and qualified by hand.

The safety contract

The explicit constraint on this plan was don't mess anything up. That is a design input, not a disclaimer, so it gets encoded as rules the work must satisfy rather than care that must be taken:

  1. Additive before subtractive. New indexes, new files, new wrappers land first. Nothing is deleted until its replacement has shipped and been exercised.
  2. Preserve the public export surface. Where a component or action is consolidated, the original named export stays and becomes a thin pass-through. Call sites do not change, so a mistake in the new primitive shows up as a localized bug rather than a compile break across twenty files.
  3. One tier per PR. Tiers are independently revertable. A bad Tier 2 revert must never take Tier 0 or Tier 1 with it.
  4. Behaviour changes are opt-in and separately flagged. The two findings that do alter what a user sees (F11 error boundaries, F03 contact-email constraint) are called out explicitly rather than smuggled in beside a refactor.

Current baseline. npx tsc --noEmit is clean. npm run lint reports one pre-existing warning (custom font in src/app/p/[slug]/proposal-view.tsx), unrelated to anything here. Both should stay exactly that clean after every tier.

Pass 1 · Data & persistence integrity

F01 — Multi-step writes are not atomic Tier 3

createProposal performs up to three dependent inserts in sequence: create the account, create the opportunity from the parsed pricing table, then insert the proposal. There is no transaction around them. If the third insert fails — a slug race, a constraint violation — you are left with an orphaned account and an orphaned opportunity, and the user sees a crash rather than a rollback.

Evidence: src/app/actions.ts:1396, :1436, :1452 — three sequential db.insert calls, no wrapper. grep for .transaction( across src/ and scripts/ returns nothing; the codebase has never used one.

Root cause, and why this is Tier 3: src/lib/db.ts builds the client from drizzle-orm/neon-http, and the HTTP driver cannot do interactive transactions at all. This isn't an oversight in the action — it's unavailable at the driver layer. db.batch() doesn't rescue it either, because each insert needs the id returned by the previous one.

Approach: @neondatabase/serverless is already a dependency at ^1.0.2, so the WebSocket path costs no new package. Add a second, lazily-constructed client — getTxDb() on drizzle-orm/neon-serverless — used only by the handful of actions that need atomicity. Every existing read keeps the current HTTP client and its connection characteristics unchanged. Migrate createProposal first, alone, and leave the rest until it has run in production for a while.

F02 — Core tables have no indexes on their filter and join keys Tier 0

companies, deals, activities and sales_tasks are all declared without an index argument, so they carry nothing but their primary key. Meanwhile relationships, proposals, payments and stripe_subscriptions — the newer tables — are all carefully indexed. The discipline is real; it just never got applied backwards.

Evidence: src/lib/schema.ts:114 (companies), :153 (deals), :172 (activities), :193 (sales_tasks) — no third argument. Compare :227, :312, :356.

This just got more relevant: the accounts list now filters on companies.stage by default and sorts on created_at, neither of which is indexed. Worth adding: companies(stage), companies(created_at), companies(stripe_customer_id), companies(plaza_key), deals(company_id), activities(company_id), activities(contact_id), activities(deal_id), activities(occurred_at), sales_tasks(company_id), sales_tasks(deal_id).

Why it's genuinely Tier 0: indexes change plan selection, never results. At today's row counts you will not feel the difference — the reason to do it now is that it is free and silent now, and becomes a production incident later.

F03 — contacts.email is uniquely indexed, which the business model contradicts Tier 2

A unique index on a nullable column is fine in Postgres — many NULLs coexist. The problem is the business rule it encodes: no two contacts may ever share an email address. This CRM sells to small local businesses, where a shared info@ or frontdesk@ mailbox covering an owner and a manager is completely ordinary.

Evidence: src/lib/schema.ts:149.

Today that insert throws a raw Postgres error which, given F11, renders as an unstyled crash page rather than "that email is already on file." Options, in increasing order of change: keep the constraint and catch the violation into a real form error; scope it to (company_id, email); or drop it to a plain non-unique index. Tier 2 because it is a deliberate change to what the system permits — it needs your call, not mine.

F04 — The signed-PDF blob sits on the hot proposals row Tier 1

proposals.signed_pdf_base64 holds multi-megabyte base64 on the same row every list and detail view reads. The protection is a rule in AGENTS.md: never select() all proposal columns. That rule is currently being honoured everywhere — I checked — but it is enforced by memory, and it is the kind of rule that survives exactly until someone adds a page in a hurry.

Evidence: src/lib/schema.ts:303. The six full-row select() calls in the codebase (src/app/accounts/page.tsx:158, src/app/accounts/[id]/page.tsx:120-122, src/app/map/page.tsx:49, src/lib/graph.ts:53) all currently avoid proposals.

Approach: move the column to a proposal_documents side table keyed by proposal_id. Only /proposals/[id]/pdf and the signing route join to it. The footgun stops being a rule and becomes structurally impossible — which is the whole point.

Pass 2 · Server-action architecture

F05 — Roughly 230 lines of identical preamble across 23 actions Tier 1

Every action in src/app/actions.ts opens with the same four moves: await requireUser(), getDb(), a null check that throws, then a hand-written formData.get() object passed to schema.parse(). Twenty-three times, in a 1,661-line file.

Evidence: src/app/actions.ts — 23 exported actions, 24 requireUser call sites, 22 z.object schemas. See :216, :249, :284, :331 for four consecutive instances of the identical block.

The cost isn't the line count, it's that authorization is copy-paste. Twenty-three chances to forget requireUser(), and the twenty-fourth action is written by whoever is in a hurry. A defineAction({ schema, handler }) wrapper makes the auth check structural — you cannot define an action without it — and collapses the FormData-to-Zod marshalling into one place.

Non-breaking because: each action keeps its exported name and its (formData: FormData) signature. Every <form action={...}> in the app is untouched.

F06 — 69 hand-maintained revalidatePath calls Tier 1

Roughly three per action, each one a manual assertion about which pages display which entity. This is a coupling that runs the wrong direction: adding a new page that reads accounts requires editing every action that writes accounts. Nothing enforces it, and the failure is silent — a stale panel, not an error.

Evidence: 69 occurrences in src/app/actions.ts. createProposal alone lists four paths plus a conditional returnPath (:1465-1471).

Approach: entity tags — revalidateTag('account:42'), revalidateTag('accounts') — so pages declare what they read and actions declare what they wrote. Migrate one entity at a time, leaving the existing revalidatePath calls in place until the tag path is proven. Redundant invalidation is harmless; missing invalidation is the bug.

F07 — Validation failure is an exception, not a form state Tier 2

schema.parse() throws. No action catches it. This is already recorded in AGENTS.md under known tech debt, and it is the direct cause of the worst user-facing behaviour in the app — see F11, which is the other half of the same problem.

The React 19 fix is useActionState with actions returning { ok: false, errors } instead of throwing. That is a genuine signature change, so it is Tier 2 and it should be done per form, starting with the highest-traffic one (account create), not as a sweep. F05's wrapper is what makes this cheap: change the wrapper's contract once and adopt it form by form.

Pass 3 · Design system & component layer

F08 — Ten near-identical auto-save components, and they have drifted Tier 1

797 lines across ten files that differ only in the name of the id prop and the union of allowed field names:

auto-save-activity-date-field.tsx    43
auto-save-company-field.tsx         140
auto-save-company-select-field.tsx  119
auto-save-contact-field.tsx          61
auto-save-deal-field.tsx             72
auto-save-deal-select-field.tsx      72
auto-save-deal-stage-field.tsx       80
auto-save-payment-account-field.tsx  61
auto-save-proposal-deal-field.tsx    60
auto-save-proposal-pin-field.tsx     89

The duplication is not the finding. The drift is. AutoSaveCompanyField carries useState + useEffect and renders an optimistic displayValue; AutoSaveContactField imports only useRef and has no optimistic state at all. Two fields that look identical on screen behave differently under the user's hands — the contact field simply doesn't acknowledge the edit the way the account field does. Nobody decided that. It is an artifact of the ninth copy being made from a different ancestor than the fourth.

Evidence: diff src/components/auto-save-company-field.tsx src/components/auto-save-contact-field.tsx — the import line and the entire displayValue state block.

Approach: two primitives — AutoSaveField and AutoSaveSelect — parameterized by (entity, id, field). Then rewrite each of the ten existing files as a four-line wrapper preserving its exact export name and props. No page changes. The behaviour converges on the better of the two (optimistic), which is a visible improvement to contact, deal, payment and proposal fields — worth calling out on the PR so it is reviewed as an intentional change rather than discovered.

F09 — Loading skeletons stop at the older half of the app Tier 0

Nine loading.tsx files exist, covering dashboard, accounts, contacts, opportunities, tasks and activities. The routes added since — /proposals, /proposals/[id], /payments, /inbox, /map — have none. Every page is force-dynamic, so those five navigate with no feedback at all while the query runs.

Evidence: find src/app -name loading.tsx returns 9 paths; none under proposals/, payments/, inbox/ or map/. src/components/skeleton.tsx (214 lines) already has the primitives.

This is the cheapest item in the plan and the most visible. It is also diagnostic: the same drift explains F08 and the stale route list in AGENTS.md (which still omits /inbox, /map and /payments). New features are not inheriting established conventions, because the conventions live in prose rather than in a scaffold.

F10 — The design system is seven CSS variables and a lot of literals Tier 2

globals.css defines --background, --foreground, two font stacks, --border-soft, --app-bg, --sidebar-bg, and three .gong-* classes. Everything else is inline Tailwind literals, and semantic colour is returned from TypeScript as class-name strings (getAccountStageTone hands back "bg-emerald-100 text-emerald-800").

Evidence: src/app/globals.css:24-37; src/lib/account-stage.ts:31-48.

It works, and the Gong-inspired direction in AGENTS.md is being held. But stage colour is now a cross-cutting concern — it appears on accounts, opportunities, proposals, payments and the map — and it is defined in four separate get*Tone functions. Promoting stage/status colour to real tokens is the enabling step for anything later: dark mode, print styles, a client-facing theme. Tier 2 because it touches rendered output; low urgency, high leverage.

Pass 4 · Reliability, safety, observability

F11 — The application has no error boundaries whatsoever Tier 2

No error.tsx. No global-error.tsx. No not-found.tsx. Anywhere.

Evidence: find src/app -name "error.tsx" -o -name "global-error.tsx" -o -name "not-found.tsx" returns empty.

Combined with F07, this is the single worst user-facing gap in the system. Every validation failure in every form is an uncaught throw with nothing to catch it, so in production it renders as Next's bare "Application error: a client-side exception has occurred." Visiting /accounts/99999 is a crash rather than a 404. A Neon cold-start timeout is a crash. Entering a duplicate contact email (F03) is a crash.

This is the highest-value item in the plan. It is three small files, it strictly reduces the set of states in which the user sees a broken page, and unlike everything else here it is felt immediately. It is Tier 2 only because it changes what renders on failure — which is the entire intent.

F12 — The public PIN gate has no rate limit Tier 2

/p/[slug] is publicly reachable and gated by a four-digit PIN compared with ===. There is no attempt counter, no backoff, no lockout. Four digits with unlimited attempts is ten thousand requests, which is minutes of scripted traffic. The internal master PIN defaults to 3067 when PROPOSAL_INTERNAL_PIN is unset, and that default is in the repository.

Evidence: src/app/p/actions.ts:47 — parsed.pin === proposal.pin; src/lib/proposal/pin.ts:20 — process.env.PROPOSAL_INTERNAL_PIN ?? "3067".

What is actually at risk is a client's statement of work and its pricing — reputational rather than catastrophic, which is why this is Tier 2 rather than an emergency. Worth noting the signing route itself is well built: it requires the PIN cookie, caps the payload at 20 MB, returns 409 on an already-signed proposal, and selects explicit columns (src/app/p/[slug]/sign/route.ts). The gate is the weak link, not the endpoint behind it.

Approach: a per-slug attempt counter with exponential backoff after five failures, plus a constant-time comparison. Set PROPOSAL_INTERNAL_PIN in the deployment environment so the committed default stops being live.

F13 — No tests, but the highest-value targets are pure functions Tier 0

AGENTS.md records this honestly. The useful observation is that the riskiest logic in the codebase is already isolated and side-effect free, so this does not require a testing strategy — just a runner and a morning.

  • parsePricingTotals / parseSections / parsePricingTable — src/lib/proposal/markdown.ts. Wrong output here silently mis-prices an auto-created opportunity.
  • src/lib/stripe/normalize.ts (208 lines) — the annual÷12 / quarterly÷3 MRR normalization that the entire revenue reconciliation rests on.
  • normalizeUsPhone, normalizeUrl, cleanOptionalText — src/app/actions.ts.
  • src/lib/referral-score.ts (151 lines).

Tier 0 by definition: adding tests cannot change production behaviour. It is also the thing that makes Tier 1 and Tier 3 safe to attempt.

F14 — Sessions cannot be revoked Tier 3

Sessions are stateless HS256 JWTs with a 14-day expiry. Deleting a user or changing a password does not invalidate their outstanding token; it stays valid for up to two weeks.

Evidence: src/lib/auth.ts — getSession() verifies the signature and reads the payload; there is no database lookup.

For a two-person team this is a theoretical concern, and it is listed last deliberately. It becomes real the moment there is a third seat or a contractor. The cheap mitigation when that day comes: a token_version integer on users, included in the JWT and compared on verify — one indexed read per request, and revocation becomes an increment.

Pass 5 · Sequencing

Ordered so that each phase makes the next one safer, and so that stopping after any phase leaves the system in a coherent state.

Phase 1 · Tier 0 — cannot break anything

Indexes, skeletons, tests

  • F02 — add the eleven missing indexes to src/lib/schema.ts, then db:generate → review SQL → db:push.
  • F09 — five loading.tsx files using the existing skeleton.tsx primitives.
  • F13 — add a test runner; cover the markdown, Stripe-normalize and format helpers.
  • Refresh the stale route list in AGENTS.md (/inbox, /map, /payments).

Exit: lint and typecheck unchanged; every route shows a skeleton; tests green.

Phase 2 · Tier 2 — the visible win

Error boundaries

  • F11 — global-error.tsx, a root error.tsx, and not-found.tsx; add notFound() calls to the [id] routes where a missing row currently falls through.

Exit: /accounts/99999 renders a real 404. A deliberately thrown action error renders a styled recovery page, not a white screen. Ships alone — it is the one item worth landing today.

Phase 3 · Tier 1 — invisible refactors, one PR each

Collapse the duplication

  • F08 — two primitives; rewrite the ten auto-save files as pass-through wrappers. Call the optimistic-state convergence out explicitly in the PR.
  • F05 — defineAction wrapper; migrate actions in small batches.
  • F04 — move signed_pdf_base64 to proposal_documents.
  • F06 — tag-based revalidation, one entity at a time, leaving the path calls in place until proven.

Exit: no page file changed except by import path. Manual pass over account, contact, opportunity and proposal detail confirms autosave still saves.

Phase 4 · Tier 2/3 — decisions, not just work

Deferred by design

  • F12 — PIN rate limiting; set PROPOSAL_INTERNAL_PIN in the environment.
  • F07 — useActionState, per form, highest-traffic first.
  • F03 — decide the contact-email rule. Needs your input.
  • F01 — transactional client for createProposal only.
  • F10 — promote stage/status colour to tokens.
  • F14 — token_version, whenever a third seat appears.

Exit: none required. This phase is a menu, and everything above it stands without it.

Risks & mitigations

RiskMitigation
The neon-serverless client (F01) behaves differently under load or cold start than the HTTP client.Add it as a second client used by one action. Reads never touch it. Rollback is deleting one import.
The F08 rewrite silently breaks an autosave field that has no test coverage.Phase 1 lands tests first. Wrappers keep exact prop shapes, so a break is a runtime bug in one field rather than a compile error everywhere — walk the four detail pages before merging.
Tag migration (F06) drops an invalidation and a panel goes stale.Additive: keep every existing revalidatePath until its tag equivalent is verified. Over-invalidation costs nothing.
db:push drift — drizzle/ generated SQL is known to be polluted relative to the live schema.Review generated SQL before pushing, as the existing workflow already requires. Index-only DDL is the safest possible thing to push first.
Moving the PDF column (F04) loses signed documents.Copy into the new table, verify counts and a byte-length checksum on every row, ship the read path, and drop the old column in a later PR — never the same one.

Out of scope

  • Multi-tenancy. Every authenticated user still sees all data. That is a product decision, not hardening, and retrofitting an org_id touches every query in the app.
  • Pagination. /accounts loads all companies and all deals and sorts in memory (src/app/accounts/page.tsx:158). Correct at current scale; worth revisiting somewhere in the low thousands of accounts. Noted, not scheduled.
  • The Gong-inspired visual direction. Explicitly preserved. F10 changes how colour is defined, never what it looks like.
  • Anything in planning/001–003. This plan hardens what exists; it does not revisit accepted decisions.
