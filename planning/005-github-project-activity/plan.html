Plan · Feature 005

GitHub project activity on Accounts

Show, per account, when that client's code last moved — so the Accounts table answers "who are we actually delivering for this week, and who has gone quiet?" without opening GitHub. Mirrored into Postgres, never fetched at render time.

Deviation 1 — the matcher scored better than the plan estimated, and the mapping became a script. The plan budgeted a hand-mapping session against a 13/18 matcher. What shipped is scripts/map-repos.mjs, which re-runs safely and only considers still-unlinked repos, so adding a client repo later proposes just that one. The three scuba links the matcher can't reach live in a MANUAL_LINKS constant inside it, which means the whole mapping is reproducible from an empty database rather than existing only as rows someone once typed. Final tally: 17 links (the extra four are the scuba cluster plus the second GT Cabinets repo), 5 internal, 14 unlinked, 4 accounts with no repo.

Deviation 2 — the orphan view moved from Phase 3 to now. It needed no new route, no new query shape, and no configuration — one filtered read against a table that already existed. Holding it back would have been sequencing for its own sake.

Lint caught a real constraint. The first version read the clock with Date.now(), which react-hooks/purity rejects inside a server component. Reusing the single new Date() the page already creates for today fixes it and is better anyway — every due pill and every push pill in a render now measures against one instant instead of two.

Why this, and the real payoff

The CRM tracks the sales half of an account well — stage, opportunities, MRR, next step, payments. It tracks the delivery half not at all. For an agency where every customer is a shipped codebase, "when did we last push for them" is the single cheapest proxy for whether an account is being served, stalling, or quietly abandoned.

Two distinct payoffs, and the second one was a surprise:

  1. Staleness detection. A customer-stage account with no push in six weeks is either finished or dropped, and the difference matters. That's the stated goal.
  2. Unbilled delivery. Comparing the org's repos against the CRM immediately surfaced work that isn't tracked as an account at all — south-pointe-dental-site, dees-autoshop-site, rg-epoxy-floor-site, bottomline-property-management. Every one of those is a repo that exists because someone was paying, or expected to. The reverse view is arguably worth more than the forward one and costs nothing extra once the data is mirrored.

Motivating case, from live data. The account Scuba Dive Utah currently shows nothing about delivery. In GitHub, the_scuba_dive_riverton_web was pushed 2026‑08‑13 — one day before this plan was written — alongside scuba-dive-riverton and scubadiveapi. Three active repos, invisible to the CRM.

Decisions taken during scoping

Push, or deploy, as the activity signal?Push in v1, schema shaped so deploys can join later.See the open question below — not a blocker, but not settled either.

Open question, deliberately non-blocking. A push can be someone poking at a branch; a deploy is the client's product actually changing. Vercel is already connected to this workspace, so last_deploy_at is reachable on the same terms as last_push_at. The v1 schema puts activity on the repo row rather than in a push-named table, so adding a second source later is a column and a GREATEST(), not a migration. If deploy turns out to be the truer signal, the UI column becomes "Last activity" and nothing else moves.

Architecture

This is the same shape as the Stripe mirror in plan 003, deliberately: an external system of record, a read-only local mirror, a reconcile script, and a webhook that keeps the mirror warm. Nothing in the request path talks to GitHub.

The economics are better than expected and worth stating plainly, because they remove the usual objection to this kind of feature:

  • GET /orgs/toprocklabs/repos?per_page=100 returns every repo with its pushed_at in a single request. There is no per-account fan-out.
  • Authenticated rate limit is 5,000/hour. A full sync costs 1–2 requests.
  • Commit detail (sha, message, author) costs one extra call per repo, or one batched GraphQL query for all of them. Phase 3, only if the hover detail proves wanted.

Schema

One new table. It copies the conventions payments established in plan 003 — external ID unique-indexed, company_id nullable so an unmatched record is never dropped, synced_at on every row.

export const projectRepos = pgTable(
  "project_repos",
  {
    id: serial("id").primaryKey(),
    // "owner/name". The stable identity; repo renames are handled by the
    // webhook's repository.full_name, or caught on the next full sync.
    fullName: text("full_name").notNull(),
    // Nullable on purpose: an unmapped repo still gets mirrored, and shows
    // up in the "delivery with no account" view. Same contract as
    // payments.company_id — never drop data for want of a match.
    companyId: integer("company_id").references(() => companies.id, {
      onDelete: "set null",
    }),
    isPrivate: boolean("is_private").default(true).notNull(),
    archived: boolean("archived").default(false).notNull(),
    htmlUrl: text("html_url"),
    // The signal. Nullable: a repo with no commits has no pushed_at.
    lastPushAt: timestamp("last_push_at", { withTimezone: true }),
    // Phase 3 detail, all nullable — the column renders without them.
    lastCommitSha: text("last_commit_sha"),
    lastCommitMessage: text("last_commit_message"),
    lastCommitAuthor: text("last_commit_author"),
    syncedAt: timestamp("synced_at", { withTimezone: true }).defaultNow().notNull(),
  },
  (table) => [
    uniqueIndex("project_repos_full_name_unique").on(table.fullName),
    index("project_repos_company_idx").on(table.companyId),
    index("project_repos_last_push_idx").on(table.lastPushAt),
  ],
);

companies gains nothing. The account's activity is MAX(last_push_at) across its repos, computed in the same aggregate query that already builds dealCounts and pipelineTotals on the accounts page — one extra select, no extra round trip per row.

Follow the repo's known DB caveat. Generated SQL under drizzle/ is polluted relative to the live schema; db:push is the source of truth. Review the generated statement before pushing and confirm it is additive only — one CREATE TABLE plus three indexes, zero DROP.

Why the mapping stays manual in v1. A 72% matcher whose misses require domain knowledge ("Riverton is Utah", "Princess Parties is the character-booking app") is exactly the wrong thing to automate first. The /inbox suggestion queue could carry the proposals later, but the one-time cost of 36 judgement calls in a Claude Code session is lower than building the flow — and doing it by hand is what produces the confident list of what a good matcher would need.

The second change: reclaim the project-URL line

The account name cell currently renders three lines, the third being a bare hostname from customerProjectUrl — low information. It becomes the repo name, linked to GitHub, with a +N affordance when an account has several. Net line count unchanged; net information up.

Phases

Phase 1 — Mirror and map Tier 0

Pure addition · nothing existing is touched

  1. projectRepos in src/lib/schema.ts; db:generate, review, db:push.
  2. scripts/sync-repos.mjs — one org call, upsert by full_name, never delete. --dry-run like the other scripts here.
  3. Mapping session in Claude Code: run the matcher, confirm the 13, resolve the 5 misses, sort the 22 orphans. Output is a set of company_id updates.

Ends with a populated table and zero user-visible change. Independently revertable by dropping one table.

Phase 2 — The column Tier 2

Visible behaviour change on /accounts

  1. MAX(last_push_at) per company folded into the existing aggregate block in src/app/accounts/page.tsx.
  2. New SortKey "lastPush"; the sort switch and sortLabels already generalize.
  3. Pill component reusing crm-due-pill tokens; repo name replaces the project-URL line.
  4. Cron: a Vercel Cron route or a GitHub Actions schedule hitting the sync. Every 30 min is generous.

Revert cost: one PR. The mirror survives the revert.

Phase 3 — Live, and the reverse view Tier 1

Additive on top of a working feature

  1. POST /api/github/webhook — org-level push hook, HMAC-verified against GITHUB_WEBHOOK_SECRET. First route.ts under src/app/api/; the signing pattern mirrors what the pending Stripe webhook will need.
  2. Commit detail (sha / message / author) on hover or the account detail page.
  3. Orphan view: repos with recent pushes and no company_id, excluding internal. Delivery you aren't tracking as revenue.
  4. Optionally a dashboard KPI: N customer accounts with no push in 30 days.

Auth & secrets

The local gh CLI is authenticated as a9austin with repo + read:org — enough for the mapping session and for running the sync locally, and it needs no new secret. It is not usable from the deployed app.

Env varWhereNotes
GITHUB_TOKEN.env.local + VercelFine-grained PAT, read-only, Contents + Metadata, scoped to toprocklabs. Matches how RESEND_API_KEY and the Stripe keys are already handled.
GITHUB_ORGbothDefaults to toprocklabs. Not hardcoded — the org name shouldn't be baked into a query.
GITHUB_WEBHOOK_SECRETphase 3 onlyHMAC verification. The route must reject unsigned requests outright.

A GitHub App would be the better long-term identity — it survives credential rotation and isn't tied to one person's account — but it is materially more setup for a read-only feature. PAT now, App if this becomes load-bearing.

Risks

RiskMitigation
A repo is renamed and the mirror keeps a dead full_name.Full sync is a reconcile, not an append: rows absent from the org listing are marked archived, never deleted, so a rename shows as one dormant row plus one new one rather than lost history.
An unlinked account reads as "abandoned" because the pill is red.Explicit fifth band. — in grey, sorted last in both directions. Called out in the UX spec because it's the easy mistake.
Token leaks into the client bundle.Only the sync script and the webhook route touch GitHub — both server-only. The page reads Postgres. No NEXT_PUBLIC_ anything.
Private repo names on a shared screen.Every repo here is already visible to anyone with CRM access, and the CRM is single-tenant by design. Worth noting, not blocking; revisit with multi-tenancy.
Push count is a bad proxy — a docs typo looks like delivery.Accepted for v1. It's a recency signal, not a productivity metric, and the failure mode (looks active when it's minor) is the benign direction. Deploys are the upgrade path.
Sync fails silently and the whole column quietly ages.synced_at is per row. If the newest synced_at is stale the column is stale, and that's detectable in one query — surface it in the orphan view rather than letting the page assert false freshness.

Out of scope

  • Commit volume, sparklines, contributor breakdowns. Trend visualisation is a real idea but it's a different feature; get the timestamp right first.
  • Any write to GitHub. Read-only mirror, same contract as plan 003. No issue creation, no PR automation.
  • In-app repo linking UI. Deferred by the v1 decision above. Becomes worth building when the org has enough repos that a Claude Code session stops being the fast path.
  • Non-GitHub sources. No GitLab, no Bitbucket. If a client's code lives elsewhere the account simply reads —.
  • Backfilling historical push activity. The mirror holds current state, not a time series.
