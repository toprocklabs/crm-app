Two bugs the verification caught. Both typechecked and would have shipped silently — the reason to test against the live vault rather than trust tsc.

1 — Authored notes' wiki-links never resolved. Only the importer wrote link rows, so a note written at /brain/new rendered every [[link]] as dangling. Fixed by adding src/lib/brain/links.ts and calling rebuildDocumentLinks / resolveDanglingLinksTo from the create and update actions. Anything that writes a body must now rebuild the graph — recorded in AGENTS.md.

2 — = any(${'{'}array{'}'}) throws in Drizzle. It expands a JS array into separate placeholders and Postgres rejects it (op ANY/ALL (array) requires array on right side). It would have thrown on every note save. Switched to inArray().

Deviation — the migration was applied as reviewed SQL, not by db:push. The repo's drizzle meta has drifted before, and db:push diffs against the live database, so it can propose drops on unrelated tables and is interactive. db:generate produced 13 statements, all CREATE; those exact statements were applied through a guard that refuses anything matching drop|truncate|delete. Net effect is identical, blast radius is not.

Deviation — a throwaway user was created to verify the auth-gated pages (qa-brain-verify), then deleted. The headless browser kept dropping its session cookie, so most verification ran by minting a session token with the app's own src/lib/auth.ts and fetching pages directly.

Phase 2 — what the API actually had to be

The plan assumed one POST. Reading the 233-line ingest prompt showed the run does more than write: it checks whether a People/ note exists before creating one, lists Projects/ Clients/ Companies/ to map a session to a note, and appends to an existing journal entry. Write-only would have forced it to blind-write and clobber hand-written notes. So the surface is:

CallPurpose
GET /api/brain/documents?folder=ProjectsList a folder — titles and paths, never bodies.
GET …?path=<path>Existence check. 404 means absent.
GET …?path=<path>&include=bodyRead a note plus its current contentSha.
POST /api/brain/documentsCreate or replace, addressed by vault path.
POST /api/brain/runsOpen a run; post again with id to close it.

Ownership is enforced by the API, not by convention. That is what makes --dangerously-skip-permissions on a scheduled agent defensible: a buggy run physically cannot destroy a hand-written note.

PathOwnerBlind write
Code/…, Sources/…the agentReplaced freely — re-running a week is idempotent.
People/…, Journal/…, Projects/…a person409 manual_authored.

To edit a human-owned note the caller must read it and resend with expectedSha — read-modify-write, which is how the journal append works. createOnly covers "ensure People/Austin.md exists" without ever overwriting. There is deliberately no force flag; adding one removes the guarantee.

All of it verified against the live database: bad token → 401, folder list, existence check, new digest → 201, agent rewriting its own digest → 200, blind write to People/Austin.md → 409, createOnly on an existing note → 409 and on a new one → 201, stale expectedSha → 409, correct one → 200, and a journal append landing on a human-authored note. Wiki-links in an agent-written digest resolve ([[Coatary]], [[Flint Gardner]]) with unknown targets left dangling. Run accounting: items_proposed incremented per write, finished_at stamped on close. Test data removed afterwards — back to 69 notes, 203 links, 0 agent-authored.

Two corrections found at the end, both worth recording

1 — The import first ran against a stale clone. Checking the repo before archiving it showed pushedAt on the remote was 2026-05-21 while the local clone's last commit was 2026-05-10. One unpulled commit held six notes that had never reached the CRM (including Companies/Vital Alignments.md, a paying account) and four that were out of date. Pulled, re-seeded, re-imported: 69 → 75 notes, 203 → 230 links. Archiving without that check would have stranded a client's notes outside the brain.

It also demonstrated the edit-guard doing its job and its limitation: a plain re-import created the 6 new notes but held back 4 bodies, because it cannot tell "a human edited this in the app" from "the source file legitimately changed". --force was correct here only because no note had been hand-edited yet.

2 — The "critical path" framing was wrong. This plan asserted that archiving the vault would break two live scheduled runs. In fact the Windows task ToprockBrain-CodeIngest-Weekly does not exist on the machine, and no note in the vault post-dates 2026-05-20. Both ingests had been dormant for three months. Phase 2 did not rescue a live pipeline; it rebuilt a dead one on better foundations. Worth knowing before deciding whether to revive either.

This is the fourth merge and the pattern is proven. Plan 002 folded in proposal_creator, plan 005 folded in GitHub delivery activity, plan 006 folded in toprock_client_notes. Two pieces are already built. suggestions (kind · jsonb payload · confidence · evidence · status · agent_run_id) is a human-in-the-loop write queue, and agent_runs (model · tokens in/out · cost · items seen/proposed) is per-run cost accounting. Most projects bolt those on late and badly. activities.source already distinguishes manual from agent.

Target architecture

Decisions

QuestionDecisionWhy
Vault or CRM as source of truth? CRM. Retire the vault. Considered and rejected: a split by data type with a one-way vault → Postgres index. It works, but it keeps two systems and two editing surfaces alive forever. Same call plan 006 made about the notes site.
Where do the scheduled agents write? Digests → the write endpoint. Record changes → /inbox. A weekly digest is a document, not a proposed change — routing five a week through an approval queue is friction with no signal. Anything that mutates a companies or deals row still goes through suggestions, where approval earns its keep.
Auth on the write endpoint? Bearer token (BRAIN_INGEST_TOKEN), not the session cookie. Both callers are headless scheduled scripts with no browser and no way to hold a JWT cookie. Plan 008's MCP server wraps the same handler behind OAuth.
How much authoring does the CRM need? Edit + create + daily journal. Anything less and Obsidian stays open in practice, which means the vault is not actually retired. The body editor already exists; only creation is new.
Retrieval depth? Postgres FTS only. Vector-ready. 69 notes. An embedding pipeline adds an API key, a re-embed step and tuning for no measurable gain at this size. The vector column drops in beside search_text later with no rewrite.
Flexible schema — how? JSONB for frontmatter. Not EAV. EAV turns every two-condition query into self-joins, stores all values as text, and thrashes indexes on write. JSONB indexes with GIN and keeps native types. Already the choice made for suggestions.payload.
Consolidation — LLM fact extraction now? No. Entity resolution first. With 69 notes and the CRM already holding the structured facts, the consolidation that pays is deterministic: make Companies/Coatary.md and the Coatary row the same thing. Temporal fact rows need an API budget and are worthless until that works.
URL identity? slug, derived from path. Vault filenames contain spaces (Drive/2026-04-24 Drive Digest.md). path stays the import identity; companies/coatary is the URL, matching the existing /meetings/[slug] convention.
Delete the vault repo? No. Freeze it. README pointing here, 69 notes committed as seed data, GitHub repo archived. Same treatment proposal_creator and toprock_client_notes got.

Schema

Two additive tables and one enum. No drops, no changes to existing tables. source reuses the existing data_source enum.

brain_documents
  id             serial pk
  path           text unique not null      -- "Companies/Coatary.md", the vault identity
  slug           text unique not null      -- "companies/coatary", the URL
  title          text not null             -- frontmatter title/name, else filename stem
  kind           brain_doc_kind not null   -- entity | digest | meta
  folder         text not null
  note_date      date                      -- from the filename prefix; null on entity notes
  body_md        text not null default ''  -- ~9 KB average. NEVER select in a list query.
  frontmatter    jsonb not null default '{}'
  content_sha    text not null
  company_id     int → companies           -- curated; survives re-import
  contact_id     int → contacts
  source         data_source not null default 'manual'
  search_text    text not null default ''
  archived_at    timestamptz               -- soft delete, never hard
  created_at, updated_at   timestamptz

  unique  brain_documents_path_unique (path)
  unique  brain_documents_slug_unique (slug)
  index   brain_documents_company_idx (company_id)
  index   brain_documents_kind_date_idx (kind, note_date)

brain_document_links                       -- the [[wiki-link]] graph
  id             serial pk
  source_doc_id  int not null → brain_documents on delete cascade
  raw_target     text not null             -- "Flint Gardner", as written
  target_doc_id  int → brain_documents on delete set null   -- null = dangling

  index   brain_document_links_source_idx (source_doc_id)
  index   brain_document_links_target_idx (target_doc_id)

enum brain_doc_kind = entity | digest | meta

The full-text index is created by hand, not by Drizzle. Drizzle 0.45 has no first-class tsvector type, db:push is this repo's source of truth, and the generated SQL is already polluted. After npm run db:push, run once:

CREATE INDEX IF NOT EXISTS brain_documents_fts_idx
  ON brain_documents USING GIN (to_tsvector('english', search_text));

Query with to_tsvector('english', search_text) @@ plainto_tsquery('english', $1), ranked by ts_rank. An expression index needs no schema column, so nothing here fights the ORM — and a vector column can join it later.

Dangling links are kept, not dropped. A [[Kanoa Imada]] pointing at a note that doesn't exist yet is exactly the signal Obsidian's graph view gives you for free: something worth writing. target_doc_id stays null and resolves itself the moment the note appears.

Body size discipline. Measured: 150 KB of bodies across 69 rows — 2.2 KB average, 12.4 KB largest (Code/2026-05-10 Code Weekly Digest.md). Smaller than the 29 KB meeting bodies plan 006 dealt with, but the digests grow every week and an unfiltered list query still drags ~150 KB today. This is the shape that bit plan 002, where a stray select() pulled megabytes of proposal PDF into a list query. Never select body_md in a list query. Third plan to write this down; enforce it in review.

The import

What it can and cannot rely on

Measured against the live vault, not assumed:

SignalReliable?Evidence
Frontmatter No 28 of 69 notes have none — every dated digest. Those that do disagree: name (34) vs title (4), type: person vs tags: [person] (37), status on 26. Long tail of 23 distinct keys.
FolderYesClean split, verified: 37 entity · 23 digest · 9 meta.
Filename date prefixYesYYYY-MM-DD on every note in a digest folder — zero exceptions across all 23.
[[wiki-links]]YesThe actual graph: 203 links, of which 182 resolve to another note by title and 21 dangle.

Measured by running src/lib/brain/frontmatter.ts over the live vault before the importer was written. Zero slug collisions across all 69. So: import every .md unconditionally, classify by folder, date from the filename, link by wiki-link and name match. Frontmatter is a JSONB bag read only when present — never a precondition.

How it runs

  1. Commit the 69 notes verbatim under scripts/seed/brain/. Same contract as scripts/seed/meetings/: the import replays from an empty database.
  2. node scripts/import-brain.mjs [--dry-run] [--force] [--only <slug>]. Idempotent by path; without --force it never overwrites an edited body. Mirrors scripts/import-meetings.mjs.
  3. node scripts/map-brain.mjs [--apply] links documents to accounts. Mirrors scripts/map-repos.mjs, including its MANUAL_LINKS const so the mapping is reproducible.

The slug matcher will not get everything. Companies/Coatary.md → Coatary is free. People/Eddy.md carries company: Vive Massage in frontmatter and needs it read; People/Alex Larson.md has no company at all. Anything the matcher can't reach goes in MANUAL_LINKS — the same decision plan 005 made for scuba-dive-riverton → Scuba Dive Utah, and for the same reason: a hand-curated link that survives every re-run beats a clever heuristic that silently mislinks.

Parser extension

src/lib/meeting/markdown.ts parses to a block tree that React renders — there is no dangerouslySetInnerHTML in the meeting path, and there must be none in the brain path either. The vault uses three things its subset lacks:

ConstructChange
[[wiki-links]]New wikilink span kind. Renders as a link in the brain, as plain text in MeetingBody.
# H1heading gains level: 1.
- [ ] / - [x]List items gain checked?: boolean.

Extend the parser and tests/meeting-markdown.test.ts — not the callers. That is the rule this repo already wrote down for exactly this situation.

Risks

RiskMitigation
The Codex daily run can't be repointed from this machine. It lives on E:\Codex Projects\toprock_brain_scheduled_run_jt, which isn't mounted here. Until someone changes it on the host machine, it keeps writing daily digests into a vault nobody reads — and those digests are simply lost. Do not enter phase 3 until it's moved. If it can't be, keep the vault writable and treat phase 3 as blocked rather than working around it. Track it as an explicit hand-off, not a to-do buried in a phase.
Retiring the vault contradicts the source plan's literal wording — "the BRAIN will store markdown files in the repo". Markdown survives as the content format in body_md; the 69 files stay committed as seed data. If a future agent genuinely needs files on disk, a generated export job is small and additive. Flagged so it's a decision, not a drift.
Obsidian's editing loop is better than a textarea. Backlink autocomplete, graph view, instant local search, offline. Replace it badly and the vault quietly reopens. Ship phase 1 fully — including create and the daily entry — before archiving anything. The honest test is whether Obsidian goes a week unopened, and that test can only run while the vault still exists.
Entity resolution mislinks quietly. A wrong company_id puts Coatary's notes on the wrong account and nobody notices. map-brain.mjs reports before it applies; unresolvable cases go in MANUAL_LINKS rather than being guessed. Unlinked is a safe state — an unlinked note is still searchable.
Scope creep into a wiki. Once notes are in the CRM it's tempting to add tags, mentions, threading, embeddings, a graph canvas. 69 notes. Ship search and backlinks; revisit when a page of results no longer fits on one screen. The same guard plan 006 set, for the same reason.
9 KB bodies in list queries. Explicit column lists on every brain query. Third plan to write this down (002, 006, now); enforce in review.

Out of scope

  • MCP server (/api/mcp) — plan 008. brain_documents + FTS is exactly what its search_brain tool wraps, and it reuses the phase-2 write handler. Nothing here may assume a single caller.
  • The agent-memory pillar — plan 009. Worth knowing first: Anthropic's Managed Agents memory stores are path-addressed markdown documents, versioned per mutation with actor and timestamp, mounted into agent containers as a filesystem. That is this vault, hosted. Build-vs-buy, decided deliberately.
  • Embeddings / pgvector — deferred by decision. Add the column when FTS demonstrably falls short.
  • LLM fact extraction — temporal valid_from/valid_to fact rows. Genuinely useful for "what did we agree in April versus now"; needs a budget; worthless before entity resolution works.
  • Markdown export back to a repo. Additive later if an agent needs files.
  • GitHub webhooks replacing the manual sync:repos poll — unrelated and unblocked.
  • Obsidian's graph canvas. Backlinks yes; a force-directed visualisation no.
