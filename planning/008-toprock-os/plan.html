Plan · Feature 008

Toprock OS

Rename the product from Toprock CRM to Toprock OS, regroup the sidebar around modules instead of a flat list of CRM pages, and give the two modules that have no surface at all a page. CRM doesn't disappear — it stops being the product and becomes one module inside it.

Why this, now

The name stopped describing the thing. Six plans in, this app holds client records, signed agreements, a Stripe payment mirror, a GitHub delivery mirror, 75 brain notes with a link graph, an agent write API and a human-in-the-loop approval queue. "CRM" describes roughly three of its twelve pages.

The nav is the evidence. Twelve flat items in CRM order, with /brain — the thing plan 007 just spent three phases building — wedged in at position four between Meetings and Contacts. That is a CRM with features bolted on, not an operating system with modules.

The rename is worth doing mostly because of what it forces. Renaming strings is cosmetic and cheap. Asking "if this is an OS, what are its modules?" is not — and the honest answer surfaces two gaps that the CRM framing kept invisible: delivery has no page (repo activity exists only as a column on /accounts), and agent runs have no page at all, despite agent_runs now recording every ingest write.

What not to touch

Do not rewrite planning/. Those 94 hits are the historical record. Plans 002–007 say "Toprock CRM" because that is what it was called when those decisions were made. Rewriting them would make the OS framing look like it existed all along, and this repo's own rule is that an accepted plan is superseded, never edited to reverse a decision. Add one dated line to planning/index.html noting the rename; leave the plans alone.

Same for docs/agentic-crm-plan.html — a historical artifact. It keeps its name.

The folder rename has a silent cost. crm-app → toprock-os on disk changes the Claude Code project key C--Users-…-crm-app, which orphans the assistant's persistent memory for this project — 11 files covering plans 002–007 and standing preferences. Recoverable by copying the directory to the new key, but only if someone remembers. That copy is a required step of phase 3, not an afterthought.

Decisions

QuestionDecisionWhy
Does "CRM" survive? Yes — as a module name. Toprock OS is the product; CRM is what the Accounts / Contacts / Opportunities group is called inside it. Keeps the word where it is accurate and retires it where it is not.
Rename the on-disk folder? Yes, and migrate the memory directory. One consistent name everywhere. The alternative — repo renamed, folder still crm-app — is the kind of mismatch that confuses you in six months.
Rename the GitHub repo? Yes. GitHub keeps redirects from the old URL. Cheap and safe. The local remote needs updating; clones elsewhere keep working.
Rename the Vercel project? Yes — the deployment is on a custom domain. The project name is cosmetic once a custom domain fronts it. Client proposal links are unaffected.
Rename with the IA change, or separately? Separate phases, one branch. Mechanical renames and design decisions review very differently. Keeping them as distinct commits means a nav regroup can be reverted without unpicking 200 string changes.
Where does agent_runs surface? A new /agents page. Plan 007 phase 2 made every agent write auditable and then left the audit invisible — a claim that "runs are auditable at /inbox" turned out to be false, because /inbox reads suggestions. Build the page or stop claiming the audit exists.

Two placements are judgment calls worth arguing about. Meetings sits under Brain rather than CRM because since plan 007 a meeting note is a knowledge artifact that happens to have an account, not a CRM record — and it already shares the markdown parser and body editor with brain notes. Tasks and Activities sit under Brain for the same reason: they are the record of what was said and what is owed, not pipeline machinery. If that reads wrong in use, moving a link between groups is a one-line change.

The collapsed rail constrains the implementation. The sidebar collapses to a 64px icon rail, and per AGENTS.md that styling is CSS-only — driven by html[data-sidebar="collapsed"] in globals.css, deliberately kept out of React state because it re-introduced a hydration mismatch and a flash of the expanded rail. Group headings must therefore hide via CSS, not by branching in the component. links is also rendered twice (desktop sidebar and mobile nav), so the grouped structure has to work in both renderers.

The two missing pages

/delivery — what we're building

Pillar 3 from the handwritten brain page. project_repos has mirrored the org's repos since plan 005, but surfaces only as a "Last push" column on /accounts and a per-account list. There is no answer to "what did we ship this week, across all clients."

  • Every non-archived repo: name, linked account, last push, last commit message and author.
  • Sorted by last_push_at, using the existing recency bands in src/lib/push-recency.ts — pure, tested, thresholds live there and nowhere else.
  • Unlinked repos ("delivery with no account") called out, since that view already exists on /accounts and belongs here instead.
  • Honest about staleness: the sync is still manual (npm run sync:repos), so the page states when it last ran rather than implying it is live.

/agents — what the machines did

agent_runs records loop, model, status, tokens in/out, cost, items seen and proposed, started and finished — and nothing renders it.

  • Runs newest first: loop, status, duration, items proposed, token and cost totals.
  • An unfinished run (no finished_at, status still running) shown as such — a run that died should look dead, not complete.
  • Link across to the suggestions a run produced, which is the connection /inbox cannot currently make.

Both are read-only list pages over tables that already exist. No schema change in this plan.

Phases

Phase 0 · Prerequisite

Land plan 007 first

Branch plan-007-toprock-brain has four unmerged commits. Renaming on top of an unmerged branch tangles a 200-file string diff with the brain work and makes both harder to review or revert.

Done when 007 is merged to main and this work starts from a clean branch off it.

Phase 1 · Tier 0 — cosmetic

Identity

The 8 UI strings, package.json name, README.md, AGENTS.md prose, and a dated rename note in planning/index.html. No identifiers, no behaviour.

Done when the app calls itself Toprock OS everywhere a person can see, and planning/ is untouched apart from the index note.

Phase 2 · Tier 1 — mechanical

Code identifiers

CrmShell → AppShell (59 usages), .crm-shell → .app-shell, crm_session → toprock_session, crm.sidebar-collapsed → toprock.sidebar-collapsed with a one-release fallback read of the old key.

Done when lint, tests and build pass, the sidebar still collapses and remembers, and logging in works after the forced logout.

Phase 3 · Tier 2 — external

Repo, folder, deployment

Rename the GitHub repo, update the local remote, rename the working directory, copy the Claude Code memory directory to the new project key, fix the one path reference in toprock-labs-brain-scheduled-run/CLAUDE.md, and rename the Vercel project.

Done when a fresh clone, the dev server, the ingest API and the assistant's memory all work under the new name.

Phase 4 · Tier 2 — design

Regroup the nav

Turn the flat links array into groups, update both renderers, and keep group headings CSS-hidden in the collapsed rail.

Done when both nav renderings show five modules, the collapsed rail still works with no hydration warning, and every existing route still resolves.

Phase 5 · Tier 0 — additive

/delivery and /agents

Two read-only pages over existing tables, each with a loading.tsx.

Done when "what shipped this week" and "what did the last ingest cost" are each answerable in one click.

Risks

RiskMitigation
The memory directory is silently orphaned by the folder rename, losing the plan 002–007 history and standing preferences. Copying it is an explicit, verified step of phase 3 — not "remember to do this". Verify by listing the new key's memory/ before deleting anything at the old one.
A .crm-shell miss shows up as broken styling rather than a build failure, and the collapsed-rail CSS is easy to half-rename. Grep for the old class after the rename and expect zero hits, then check the sidebar expanded and collapsed by eye. Not a test the suite can run.
The rename diff buries a real change. A 200-file mechanical diff is where a behavioural edit hides. Phases 1 and 2 are string and identifier changes only, in their own commits. Anything that changes behaviour belongs in phase 4 or 5.
Regrouping is a matter of taste and the first arrangement will be wrong somewhere — Meetings and Tasks especially. No route moves, so a link changing groups is one line. Ship the arrangement, use it for a week, adjust.
Two new pages is two new untested surfaces in a plan whose point was a rename. Both are read-only lists over existing tables with no schema change, and both have a loading.tsx per the repo rule. If phase 5 slips, phases 1–4 still stand alone.
An OS that is mostly empty rooms. Five modules where two have one page each can read as scaffolding. That is the honest current shape, and naming it is the point — the empty rooms are what the CRM framing was hiding. Do not invent pages to fill the grid.

Out of scope

  • Rewriting plans 002–007. Historical record.
  • Renaming database objects. No table, column or enum changes. Renaming the Neon database itself is pure risk for zero benefit.
  • Renaming routes. /accounts, /brain and the rest keep their URLs; only their grouping changes.
  • The gong-panel class and the Gong-inspired design direction — unrelated to the name, and AGENTS.md pins the visual direction deliberately.
  • Pillar 2 (agent memory). Still the next real build, deferred by this plan rather than replaced by it.
  • Deploying. Phase 3 renames the Vercel project; shipping remains a separate, deliberate act.
