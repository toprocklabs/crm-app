Toprock CRM

What this project is

A lightweight CRM (product label Toprock CRM) covering accounts, contacts, opportunities, tasks, and activities. The current product direction is a Gong-inspired revenue-workspace UI — a dark utility sidebar, a bright analytics canvas, crisp white panels, and a cyan/blue accent system — favoring dense-but-readable information hierarchy over a generic SaaS card layout.

Tech stack

  • Framework: Next.js 16.x (App Router), TypeScript, Tailwind. Server-rendered route pages (force-dynamic) with server actions for all writes. Note: this is Next.js 16 — check node_modules/next/dist/docs/ before relying on older framework patterns.
  • Data layer: Drizzle ORM over Neon Postgres. Schema + enums in src/lib/schema.ts; shared client in src/lib/db.ts. db:push is the source of truth for the live schema.
  • Auth: custom username/password login with a signed JWT cookie session (src/lib/auth.ts). Passwords hashed with bcrypt (bcryptjs).

Conventions & standards

  • Prefer server components for pages and data reads. Keep mutations in server actions ("use server") and validate inputs with Zod. Gate every write with requireUser().
  • UI vs. DB terminology is deliberate: UI label Account = table companies; UI label Opportunity = table deals. Keep this mapping consistent.
  • Phone numbers normalize to US format (###) ###-#### in actions; preserve the Call (tel:) button behavior and contact blur-autosave behavior when touching those areas.
  • Create/log forms use CollapsibleFormSection, default collapsed, auto-closing on submit. When adding activity logging, set returnPath so the page revalidates.
  • If adding/renaming routes, update the top nav in src/components/crm-shell.tsx.
  • Validation before hand-off: npm run lint and npm run build. If schema touched, regenerate + apply the migration; if auth touched, verify /login and guarded redirects. No automated test suite yet — quality relies on lint/build + manual verification.

Database change workflow

  • Edit src/lib/schema.ts → npm run db:generate → review SQL in drizzle/ → npm run db:push → npm run build and verify affected pages.
  • Generated migration SQL is known to be polluted/drifted; treat db:push against the live DB as the authoritative state.

Non-negotiables

  • Never store plaintext passwords — always bcrypt. Keep AUTH_SECRET (≥32 chars) and DB credentials in .env.local only.
  • Preserve the /customers → /accounts (and /customers/[id]) backward-compat redirects unless explicitly removing them.
  • Do not reintroduce glossy/glassy gradients or duplicative summary panels; preserve the approved Gong-inspired UI direction unless explicitly redesigning.

Known constraints / tech debt

  • Single-tenant: all authenticated users see all data; no per-user/org authorization boundary yet.
  • Contact-to-opportunity linking is partial (deals.primaryContactId not set in all create flows).
  • Minimal error UX — server-action validation failures generally throw rather than surfacing inline.
  • Phone normalization assumes US numbers only; non-US formats are rejected.
